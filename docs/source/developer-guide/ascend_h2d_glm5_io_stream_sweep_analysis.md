# Ascend H2D GLM5 简化 IO 模型 Stream Sweep 结果分析

## 摘要

本轮 toolkit 测试将 CE 和 FFTS Direct H2D 的物理 IO 数量对齐，并同时扫描序列长度、设备数和 stream 数。完整数据包含 168 组组合，所有组合均执行成功。

核心结论如下：

1. 最佳 stream 数随 IO 数量增加而上移，不能用一个固定 stream 数覆盖 8K、64K、128K 三种负载。
2. 8K 负载的有效区间是 4～8 streams；继续增加 stream 会被调度、event 和同步开销反噬。
3. 64K 负载的有效区间是 16～32 streams。其中 CE 用 32 streams 最稳健，FFTS 用 16 streams 即可接近所有场景的峰值。
4. 128K 负载的有效区间是 16～64 streams。CE 用 16 streams 已能达到各场景峰值的 96.2% 以上；FFTS 的最优点受 Host 类型和设备数影响，需要在 32 与 64 之间选择。
5. 在物理 32K IO 数一致的前提下，FFTS 的峰值带宽是 CE 峰值带宽的 4.15～6.65 倍。但该差异同时包含 Direct H2D 路径收益和“三个 IO 聚合为一个 task/launch”的收益，不能只归因于 SDMA 引擎。
6. CE 4-stream 在 64K、128K，尤其 8 卡场景中出现约 100～127ms 的周期性 Copy 长尾。日志带宽按 Copy Avg 计算，因此这些长尾显著压低了平均带宽。
7. 这份结果证明 toolkit 微基准中的多 stream 收益和拐点，不直接证明 CacheStore 或服务场景应该采用相同 stream 数。

序列长度与 IO 数的对应关系如下：

| 序列长度 | Shard 数 | 每卡 32K IO 数 | 每卡传输量 | 8 卡聚合传输量 | CE 参数 | FFTS 参数 |
|---:|---:|---:|---:|---:|---|---|
| 8K | 64 | 192 | 6 MiB | 48 MiB | `-n 192` | `-n 64 -f 3` |
| 64K | 512 | 1536 | 48 MiB | 384 MiB | `-n 1536` | `-n 512 -f 3` |
| 128K | 1024 | 3072 | 96 MiB | 768 MiB | `-n 3072` | `-n 1024 -f 3` |

CE 与 FFTS 在同一行中的物理 IO 数和传输字节数一致，但提交粒度不同：

- CE 对每个 32K IO 执行一次异步 memcpy 提交。
- FFTS 将同一 shard 的 3 个 32K IO 组织成一个 task，并通过一次 dispatcher launch 提交。

因此，本测试可以公平比较两条路径传输相同字节数时的端到端 toolkit 表现，但 CE 与 FFTS 的 Submit 绝对值仍包含不同提交粒度的影响。

### 1.1 测试是否循环读取

代码中的 buffer、stream 和 task 拓扑只在 `Prepare` 阶段创建一次。随后执行：

1. 3 次 warmup。
2. 128 次正式 iteration。
3. 每次 iteration 都调用同一个 `DoCopyOnce`，复用相同的 Host 源地址和 Device 目标地址。

因此，这是一种循环读取同一批 Host buffer 的微基准。包含 warmup 在内，每个 case 实际将同一段源数据复制 131 次，其中只有后 128 次进入统计。

测试不会在每轮换一批新的 shard 数据，也不会在每轮重新分配、映射或注册 Host buffer。Host 内存初始化和 Host register 发生在计时循环之前，因此 Submit/Copy 统计不包含这些准备成本。

这个特征意味着：

- 数据页在正式测试前已经被 warmup 访问，属于驻留、热页状态。
- 测到的是重复 Host-to-Device 传输能力，不是首次访问时延。
- 测试不包含存储读取、缺页恢复、backend wait 或 CacheStore 排队。
- 不能把 Copy Avg 直接解释成真实请求从存储加载一批新 KV 的完整时延。

### 1.2 CE 的 IO 遍历方式

CE 将 `-n` 解释为物理 32K IO 数。代码先把连续 Host buffer 按 stream 数近似均分：

- 每个 stream 获得一段连续的 IO 范围。
- 每个 stream 内部按地址顺序遍历这段范围。
- 每个 32K IO 单独调用一次异步 memcpy。
- 所有 IO 提交后，通过 end event 和主 stream 同步等待全部 stream 完成。

例如 64K 序列对应每卡 1536 个 32K IO。使用 32 streams 时，每个 stream 大约负责 48 个连续 IO；下一轮 iteration 仍然读取完全相同的 48 个 offset。

### 1.3 FFTS 的 IO 遍历方式

FFTS 先将连续的 3 个 32K fragment 组成一个 shard task，再将 task 按 round-robin 分配到 stream：

- 8K：192 个 fragment，组成 64 个 task。
- 64K：1536 个 fragment，组成 512 个 task。
- 128K：3072 个 fragment，组成 1024 个 task。

每个 stream 内部循环处理分配给自己的 task；每个 task 先构造 3 个 copy spec，再执行一次 dispatcher launch。下一轮 iteration 会重新提交同一组 task，源 fragment 的 offset 不变。

FFTS 的有效 stream 数不会超过 task 数。因此 8K 请求 S128 时，代码实际只创建 64 个 stream，不能把这组数据当成真正的 128-stream 结果。

### 1.4 Shared 多卡是否读取同一块内存

是。`one_share_host_to_all_device` 的代码流程是：

1. 父进程创建一个 POSIX shared-memory 对象，容量仅为一份每卡 workload，即 6 MiB、48 MiB 或 96 MiB。
2. 父进程初始化这一个共享对象。
3. 测试为每张卡 fork 一个子进程。
4. 每个子进程使用相同 shared-memory 名称映射完整区域，并针对自己的设备注册该映射。
5. 每个子进程都从 fragment 0 开始，读取完全相同的 offset 范围。
6. 每张卡写入各自独立的 Device buffer。

各子进程中的虚拟地址可以不同，但底层 backing pages 是同一个共享内存对象。8 卡不是把一份 Host 数据切成八段，而是八张卡同时读取同一份完整数据：

```text
一份 Shared Host 区域
    ├── 完整读取 → Device 0 独立目标区
    ├── 完整读取 → Device 1 独立目标区
    ├── ...
    └── 完整读取 → Device 7 独立目标区
```

所以 Shared 8 卡场景测试的是“一份 Host backing 向多卡并发 fan-out”，不是多卡分片读取。日志 Count 和 BW 仍将 8 张卡的 H2D 流量全部计入：例如每卡 96 MiB 时，聚合流量按 768 MiB 计算，即使 Host 侧只有一份 96 MiB backing。

8 卡结果按每轮最慢子进程的 Submit/Copy 时间合并。因此其带宽口径是“总 H2D 字节数除以最慢卡完成时间”，可以衡量 fan-out 聚合吞吐，但不能解释成从 Host 内存读取了 8 份互不相同的数据。

### 1.5 O_DIRECT 多卡是否共享 Host 数据

不共享。`all_odirect_host_to_all_device` 的每个设备子进程都会创建自己的匿名 Host mapping，并为对应设备单独注册。不同设备的源内容模式相同，但 backing memory 彼此独立。

这里的 O_DIRECT 表示适配 UCM O_DIRECT buffer 布局的页对齐、huge-page 风格匿名映射，并不执行文件 `read`、`pread` 或真正的 O_DIRECT 存储 IO。因此 O_DIRECT 与 Shared 的对比实质上是：

- 每卡独立 Host backing。
- 多卡共享同一 Host backing。

而不是“磁盘 IO”与“内存 IO”的对比。

### 1.6 对结果分析的影响

结合上述代码模式，需要对结果做以下约束：

- FFTS/CE 的 stream 曲线是在热内存、重复地址条件下测得，主要反映提交和 H2D 调度能力。
- Shared 8 卡的结果包含同一 backing pages 被多卡并发读取的特征，可能受到 Host 内存控制器、NUMA、注册映射和多卡 fan-out 行为影响。
- O_DIRECT 8 卡使用独立 backing，更接近每卡拥有独立 Host 数据，但仍没有实际 backend IO。
- FFTS 相比 CE 的低 Submit 不仅来自 copy 方法，还来自 3 个 fragment 聚合成一次 launch。
- CE 的约 100ms 长尾发生在 buffer 创建、初始化和注册之后，也不是存储读取造成的；后续应优先检查每轮提交、Runtime 等待、进程调度和 stream/event 同步。

## 2. 指标解释

### 2.1 Submit

`Submit(us)` 是 Host 侧遍历 context 并完成异步任务下发所花费的墙钟时间，不代表数据已经传输完成。

### 2.2 Copy

`Copy(us)` 使用设备 event 统计从起始 event 到所有 stream 完成的总体 makespan。多 stream 可以让不同任务重叠执行，因此 Copy 时间可能在 Submit 不下降甚至上升时继续下降。

Submit 与设备执行存在重叠，不能将 Submit 和 Copy 直接相加。

### 2.3 Bandwidth

带宽使用总传输字节数除以 Copy Avg。日志列名为 `GB/s`，计算公式实际使用 1024 的三次方换算，数值口径更接近 GiB/s。

8 卡场景按每轮最慢设备的时间合并，并用 8 卡总字节数计算聚合带宽。因此，8 卡带宽反映 slowest-device makespan，不是单卡带宽的简单平均。

## 6. 下发时间、完成时延与带宽的联合分析

为了避免只看带宽，本节将候选 stream 相对同场景 S1 的三项平均变化放在一起。每一行先分别对 O_DIRECT/Shared、单卡/8 卡做相对变化，再对四个场景等权平均。

| 方法 | 序列 | 候选 Stream | Submit Avg 变化 | Copy Avg 变化 | BW 变化 |
|---|---:|---:|---:|---:|---:|
| CE | 8K | 8 | -6.3% | -41.6% | +74.4% |
| CE | 64K | 32 | +14.6% | -53.9% | +117.6% |
| CE | 128K | 16 | -72.0% | -55.2% | +124.5% |
| FFTS | 8K | 4 | +13.8% | -26.7% | +36.9% |
| FFTS | 64K | 16 | -0.7% | -48.2% | +93.6% |
| FFTS | 128K | 32 | +8.5% | -45.3% | +84.0% |

### 6.1 下发时间

增加 stream 并不必然降低 Submit：

- CE 64K 从 S1 增加到 S32 后，Submit 平均增加 14.6%，但 Copy 时延下降 53.9%，所以带宽仍提高 117.6%。这是用更多 Host/Runtime 下发开销换取设备侧并行的典型情况。
- FFTS 8K 从 S1 增加到 S4 后，Submit 增加 13.8%，Copy 时延下降 26.7%，最终带宽提高 36.9%。
- FFTS 128K 使用 S32 时，Submit 增加 8.5%，Copy 时延下降 45.3%，带宽提高 84.0%。
- CE 128K 是例外：S1 的 Submit 本身已达到 11～20ms，并伴随明显慢路径；增加到 S16 后，Submit 和 Copy 同时下降。

因此，Submit 更适合判断 Host 下发成本和 Runtime 压力，不能单独用于判断最终吞吐。FFTS 的 Submit 较低还包含每三个物理 IO 聚合为一个 task 的收益。

### 6.2 完成时延

Copy Avg 是本轮最接近“本批 IO 完成时延”的指标。候选 stream 对三种序列的 Copy Avg 都有明显改善：

- 8K：CE S8 平均降低 41.6%，FFTS S4 平均降低 26.7%。
- 64K：CE S32 平均降低 53.9%，FFTS S16 平均降低 48.2%。
- 128K：CE S16 平均降低 55.2%，FFTS S32 平均降低 45.3%。

在各自峰值点，FFTS 的 Copy Avg 是 CE 的约四分之一到六分之一。因为两边物理字节数相同，Copy 时延比值与带宽比值互为倒数。例如 O_DIRECT 64K、8 卡场景中，CE S16 的 Copy Avg 为 10.295ms，FFTS S16 为 2.109ms，对应带宽分别为 36.425 和 177.809。

需要注意，Copy 通过设备 event 统计，并且覆盖 Host 持续提交期间的设备执行。它不是“Submit 结束后再额外等待的纯 DMA 时间”，也不能与 Submit 直接相加形成总时延。

### 6.3 带宽

带宽直接由固定字节数和 Copy Avg 得到，因此变化方向与 Copy 时延相反：

- 小负载 8K 很快达到饱和，继续增加 stream 会同时恶化 Submit、Copy 和带宽。
- 64K 在 S16～S32 达到平台区，CE 和 FFTS 均接近两倍于 S1 的带宽。
- 128K 能继续利用较高并行度，但 S32 与 S64 的差距已经很小，S128 普遍回落。

三项指标联合说明：最佳 stream 的判据应首先保证 Copy/BW 接近峰值，再在相近带宽点中选择 Submit 更低、stream 更少的配置，而不是单独追求最低 Submit 或绝对最高 BW。

## 7. 序列长度决定最佳 Stream 区间

### 7.1 8K：4～8 streams

8K 每卡只有 192 个物理 IO，FFTS 只有 64 个可独立调度 task。此时 stream 很快超过有效并行需求。

CE 使用 8 streams 时：

- 四个场景平均带宽比 S1 提升 74.4%。
- 平均达到各场景峰值的 99.7%。
- 最差场景也达到峰值的 98.6%。
- Submit 相比 S1 平均下降 6.3%。

FFTS 使用 4 streams 时：

- 四个场景平均带宽比 S1 提升 36.9%。
- 平均达到各场景峰值的 94.7%。
- O_DIRECT 8 卡在 S8 达峰，因此统一使用 S4 时，该场景只能达到峰值的 78.6%。

当 FFTS 增加到 S16 时，平均带宽已经比 S1 下降 15.2%，Submit 则增加 133.6%。S32、S64 的退化更明显。

结论：8K 不适合高 stream。CE 推荐 S8；FFTS 一般推荐 S4，O_DIRECT 8 卡可使用 S8。

### 7.2 64K：16～32 streams

64K 每卡有 1536 个物理 IO、512 个 FFTS task，能够持续填充更多 stream。

CE 使用 32 streams 时：

- 四个场景平均带宽比 S1 提升 117.6%。
- 平均达到各场景峰值的 98.5%。
- 最差场景达到峰值的 94.1%。

FFTS 使用 16 streams 时：

- 四个场景平均带宽比 S1 提升 93.6%。
- 平均达到各场景峰值的 99.1%。
- 最差场景达到峰值的 98.4%。
- Submit 相比 S1 基本不变，平均下降 0.7%。

FFTS 从 S16 增加到 S32，平均峰值覆盖率从 99.1% 变为 98.3%，没有获得稳定收益；增加到 S64 后开始明显退化。

结论：64K 的推荐配置是 CE S32、FFTS S16。

### 7.3 128K：16～64 streams

128K 每卡有 3072 个物理 IO、1024 个 FFTS task，高并行度可以被更充分地利用。

CE 使用 16 streams 时：

- 四个场景平均带宽比 S1 提升 124.5%。
- 平均达到各场景峰值的 98.0%。
- 最差场景达到峰值的 96.2%。
- Submit 相比 S1 平均下降 72.0%。

CE S64 的平均峰值覆盖率为 98.4%，只比 S16 高 0.4 个百分点，但 stream 数增加四倍。因此从资源效率和稳定性角度，S16 更适合作为统一候选。

FFTS 的 S32 和 S64 平均峰值覆盖率分别为 93.9% 和 94.2%，不存在一个同时覆盖所有场景的单一最佳值：

- O_DIRECT 单卡：S64 最优。
- O_DIRECT 8 卡：S32 最优。
- Shared 单卡：S32 最优。
- Shared 8 卡：S64 最优。

结论：128K 的 CE 统一候选是 S16；FFTS 应在 S32、S64 之间按 Host 类型和设备数选择。

## 8. 对 CE 4-stream 与 FFTS 1-stream 的解释

### 8.1 CE 4-stream

CE 默认 S4 对小负载比较合理：

- 8K 平均可以获得各场景峰值的 94.1%。
- 继续增加到 S8 的平均收益有限。

但 S4 无法覆盖中长序列：

- 64K 平均只达到峰值的 46.1%。
- 128K 平均只达到峰值的 43.7%。

这里既有并行度不足，也有 S4 的周期性长尾问题。不能仅根据 S4 的平均带宽断定 CE 引擎能力低，还需要单独解释长尾来源。

### 8.2 FFTS 1-stream

FFTS S1 的峰值覆盖率随负载增大而下降：

- 8K：平均达到峰值的 69.0%。
- 64K：平均达到峰值的 51.4%。
- 128K：平均达到峰值的 51.1%。

这说明 S1 对小负载仍有一定合理性，但在 64K、128K 的多 task 场景中只能发挥约一半峰值吞吐。当前 toolkit 数据不支持“FFTS Direct H2D 天然不需要多 stream”的判断。

### 8.3 为什么 FFTS Submit 更低

在各自峰值点，FFTS 的 Submit Avg 在 12 个对照场景中都低于 CE。主要原因不能只解释为 SDMA 更快：

- 两边物理 IO 数相同。
- CE 按 32K IO 逐个提交。
- FFTS 每次 launch 聚合 3 个 32K IO。
- FFTS 的 Host 提交次数约为 CE 的三分之一。

所以 FFTS 的结果同时体现了 Direct H2D copy 路径和 shard 内 IO 聚合的共同收益。

## 9. CE 4-stream 长尾与稳定性

CE 在 64K、128K 的 S4 场景中出现明显的约 100ms 周期性长尾，8 卡最突出：

| Host | 序列 | 设备 | Stream | Copy Avg | Copy P50 | Copy P90 | Copy Max | BW |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| O_DIRECT | 64K | 8 | 4 | 36,245us | 11,792us | 108,073us | 111,620us | 10.346 |
| Shared | 64K | 8 | 4 | 37,114us | 13,426us | 109,763us | 112,134us | 10.104 |
| O_DIRECT | 128K | 8 | 4 | 64,391us | 23,367us | 118,007us | 120,613us | 11.648 |
| Shared | 128K | 8 | 4 | 87,891us | 116,219us | 123,303us | 127,184us | 8.533 |

其中前三组的 Avg 与 P50 差距很大，且 P90 已进入 100ms 量级，说明不是单个偶发最大值，而是至少一部分 iteration 稳定进入了慢路径。Shared 128K、8 卡、S4 更严重，P50 本身已经达到 116ms。

由于 BW 使用 Copy Avg 计算，这些慢 iteration 会直接压低日志带宽。这也是 CE S4 在 64K、128K 上看起来显著弱于 S8/S16/S32 的重要原因之一。

当前数据只能确认长尾存在，不能仅凭汇总统计判断其根因。可能涉及多进程调度、Runtime 内部等待、stream/event 依赖或 CE 队列竞争，需要结合逐 iteration 日志和 msprof 时间线继续定位。

## 10. Host 类型与设备扩展

### 10.1 Host 类型

CE 对 Host 类型更敏感：

- 单卡峰值下，O_DIRECT 相比 Shared 高约 21%～38%，8K 除外。
- 8 卡峰值下，O_DIRECT 在 64K、128K 比 Shared 高约 20%。

FFTS 对 Host 类型相对不敏感：

- 64K 单卡和 8 卡的 O_DIRECT、Shared 峰值接近。
- Shared 在 8K、128K 的 8 卡场景中反而更高。

这表明 FFTS Direct H2D 对 Host buffer 类型的敏感度低于 CE，但还不能推导到真实 Posix backend，因为 toolkit 中的数据已经位于可直接访问的 Host buffer。

### 10.2 1 卡到 8 卡扩展

按各场景自身最佳 stream 比较，8 卡聚合带宽相对单卡提升如下：

| Host | 方法 | 8K | 64K | 128K |
|---|---|---:|---:|---:|
| O_DIRECT | CE | 6.21x | 6.56x | 6.95x |
| O_DIRECT | FFTS | 5.95x | 6.62x | 5.67x |
| Shared | CE | 8.06x | 6.60x | 7.39x |
| Shared | FFTS | 7.24x | 6.49x | 6.23x |

除 Shared CE 8K 外，多数场景为 5.67～7.39 倍，未达到理想的 8 倍线性扩展。这说明多卡共享 Host、PCIe/内存系统、进程调度或最慢卡拖尾仍会限制聚合带宽。

## 11. 原理层面的解释

本轮数据呈现出典型的“并行收益—饱和—反噬”曲线。

### 11.1 并行收益阶段

当 task 数足够多时，增加 stream 可以提高设备侧并发和任务重叠，缩短最慢 stream 完成时间。64K、128K 的 S16/S32/S64 都处于这一阶段。

### 11.2 饱和阶段

当 copy engine、内存链路或调度队列已经被填满后，继续增加 stream 不再降低 Copy 时间。64K 的 S16～S32、128K 的 S16～S64 基本属于平台区。

### 11.3 反噬阶段

stream 过多时，每条 stream 分到的 task 数减少，但 stream、event、wait 和 context 管理成本继续增加。

8K FFTS 只有 64 个 task：

- S4 时每 stream 约 16 个 task。
- S8 时每 stream 约 8 个 task。
- S32 时每 stream 约 2 个 task。
- S64 时每 stream 只有 1 个 task。

因此 8K 在 S16 之后快速退化。64K 和 128K task 更多，拐点相应后移。

## 12. 建议配置

仅针对本轮 toolkit 简化 GLM5 IO 模型，建议优先验证以下配置：

| 序列长度 | CE 候选 | FFTS 候选 | 说明 |
|---:|---:|---:|---|
| 8K | 8 | 4；O_DIRECT 8 卡可用 8 | 小 IO 数，不宜使用高 stream |
| 64K | 32 | 16 | 两者都能覆盖至少 94% 的场景峰值，FFTS S16 覆盖度更高 |
| 128K | 16 | 32 或 64 | CE S16 是资源效率更高的统一值；FFTS 需按场景选择 |

如果生产配置暂时只能使用一个固定值：

- CE 可以优先验证 16 streams。它不是 8K 的绝对峰值，但能避免 64K、128K 的并行度不足，同时比 32/64 更节省 stream 资源。
- FFTS 不建议直接固定为 32 或 64，因为 8K 会严重退化。应优先考虑按 task 数或 IO 数自适应选择 stream。

一个可用于后续验证的初始自适应规则是：

- FFTS task 数不超过 64：4 streams，O_DIRECT 8 卡可尝试 8。
- FFTS task 数约 512：16 streams。
- FFTS task 数约 1024：32 streams 起步，特定 Shared 8 卡或 O_DIRECT 单卡场景再尝试 64。

这只是基于当前三个采样点得到的分段规则，尚不能直接进入生产代码。

## 13. 下一步验证建议

### 13.1 Toolkit 复测

优先复测以下点，每点至少执行三轮，并随机化或反向执行 stream 顺序：

- CE：64K、8 卡、S4/S16/S32。
- CE：128K、8 卡、S4/S16/S32/S64。
- FFTS：8K、S4/S8/S16。
- FFTS：64K、S16/S32/S64。
- FFTS：128K、S32/S64/S128。

复测应保留逐 iteration Submit 和 Copy 原始值，而不仅是 Min/Max/Avg/P50/P90，以确认 CE 的 100ms 长尾是周期性、随机性还是固定阶段触发。

### 13.2 msprof

对 CE 4-stream 长尾点和相邻正常点进行对照，观察：

- Host API 下发时间线。
- 每个 stream 的任务密度与空洞。
- event/wait 依赖链。
- CE/SDMA 引擎活跃区间。
- Host 侧进程是否出现约 100ms 调度停顿。
- 长尾发生时是提交阻塞、设备排队还是同步等待。

### 13.3 Cache Fake

Toolkit 复测稳定后，将候选 stream 带入 Cache Fake：

- 保留 CacheStore 队列、shard/task 调度和 H2D 路径。
- 分别记录 backend-ready、H2D submit、H2D sync、load completion。
- 验证 toolkit 的最佳 stream 是否仍能降低 Cache 层 makespan。

### 13.4 服务端到端

最终在真实服务中验证：

- TTFT。
- Cache load duration。
- TP/DP 各 rank 最慢完成时间。
- Host 内存、CPU 和 Runtime 开销。
- 不同序列长度混合时固定 stream 与自适应 stream 的差异。

## 14. 结论边界

本轮测试可以证明：

- 固定物理 IO 数后，CE 和 FFTS 都存在明显的多 stream 收益。
- 最佳 stream 与 shard/task 数强相关。
- FFTS 1-stream 在 64K、128K toolkit workload 下明显未达到吞吐峰值。
- CE 4-stream 在长序列下既存在并行度不足，也存在需要继续定位的长尾问题。
- FFTS 的优势包含 Direct H2D 和 shard 内三 IO 聚合两部分。

本轮测试不能证明：

- Cache Fake、Posix backend 或真实服务会获得相同比例的带宽提升。
- 生产环境应该无条件将 CE 改为 16 或将 FFTS 改为 32/64 streams。
- CE 100ms 长尾的具体根因已经确定。

因此，当前最合理的结论是：toolkit 阶段已经给出了清晰的候选区间和异常点，下一步应先复测 CE 长尾，再使用 Cache Fake 验证队列与 H2D makespan，最后进入服务 TTFT 验证。
